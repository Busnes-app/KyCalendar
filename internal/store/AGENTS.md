# Storage Layer

## Purpose
Provides the unified Database Abstraction Layer (DAL) supporting pluggable backends (SQLite zero-CGO default and PostgreSQL enterprise) with automated dialect-aware migrations.

## Ownership
Owns data models, store interfaces (`UserStore`, `SessionStore`, `DeviceStore`, `GroupStore`, `AuditStore`, `SettingsStore`, `CalendarStore`, `AppPasswordStore`), dialect translations, and schema migrations.

## Local Contracts
- `CompletePasswordChange` atomically compares the old password, updates a flagged local account, clears the flag, deletes sessions/MFA challenges/device pairings/app passwords and records `auth.password_changed`. Session/MFA issuance locks the same user row against the verified hash; MFA challenges persist the creation-time password hash, and consumption returns that snapshot to reject stale completions. Migration 4 discards preexisting challenges because their credential snapshot is unknown.
- `ResetAdminPassword` reactivates a local administrator with the replacement flag set and shares the atomic grant purge and audit path with `CompletePasswordChange`; it also works for disabled accounts.
- `RenameUser` updates only a local account's `username` (never a whole-row write, so a concurrent password change is not undone) and audits `user.renamed` with the given actor (`system` from the CLI, the acting admin from the People screen) in the same transaction.
- Usernames are unique ignoring case. `CreateUser` and `RenameUser` look for a case twin of another account inside `lockedTx("user-names")` and return `ErrAlreadyExists` (every provider: CLI, People screen, SCIM, SSO provisioning); `RenameUser` checks only when the name changes ignoring case, so a legacy twin can still change its own case. `UpdateSCIMUser` (SCIM replace and patch) and `UpdateUser` do not check. `TestCaseTwinCreateWaitsForTheNameLock` (Postgres) pins the lock.
- `ResetPassword` is the same operator reset (`operatorReset`: hash, replacement flag, grant purge, `auth.password_changed` audit, one transaction) for any local account, without touching role or status; a missing or non-local account is `ErrNotFound`.
- `SetRole` and `SetStatus` change a local account inside `lockedTx("local-admins")`: the row update comes first (it blocks `withPassword` until commit), then its sessions, MFA challenges, device pairings and app passwords are deleted in the same transaction, and refuse (`ErrLastAdmin`) a change that leaves no active local administrator; SSO administrators do not count, because the local admin is the way back in when the IdP is gone. `UpdateProfile` writes only a local account's display name and email. `TestConcurrentDemotionKeepsOneLocalAdmin` pins the lock on both backends. `SetRole`, `SetStatus`, `ResetPassword` and `CreateUserAs` take an `Actor`: `AdminActor(userID, sessionHash)` is rechecked first inside the write's transaction (`checkActor`: still `role = 'admin'`, `status = 'active'`, and that session row live and theirs) or the write is `ErrActorRevoked`; the recheck is a no-op `UPDATE` of the actor's users row, then of that session row, so both stay locked to commit. Every revocation updates the users row first (`SetSSORole`, `RevokeSSOUser`, `UpdateSCIMUser`, `changeAccess`, `BindSignIn`, `ReattachSSOUser`, `withPassword`; logout deletes only the session row, which the recheck also holds), so a revocation committed first refuses the write and one arriving later waits for it. Lock order, every path: advisory keys (`local-admins`, then `user-names`), the actor's users row, the actor's session row, then target rows; SSO revocations lock one users row and take no advisory key, so no cycle forms. `TestActorRowSerialisesWithSSORevocation` (Postgres) pins both interleavings for reattach and disable against `SetSSORole` and `RevokeSSOUser`; `System` (CLI `reset-password`, `CreateUser`, `ResetAdminPassword`) skips it and the zero `Actor` is refused. `ResetPassword` by an admin holds `local-admins`; `CreateUserAs` holds `local-admins` then `user-names` (`lockedTx` takes keys in order; local-admins always first). `TestAccessWritesRecheckTheActor` and `TestActorRecheckWaitsForTheAccessLock` (Postgres) pin it. `TestRoleChangeRevokesASessionIssuedDuringIt` (Postgres) pins the order.
- `ReattachSSOUser(actor, userID, binding)` is the admin reattach, one transaction under `lockedTx("local-admins")`: `checkActor`, then the non-local row's `sso_issuer = binding` and `status = 'active'` only where `sso_issuer <> binding` (row first), then its grants (`revokeGrants`); role untouched; returns the previous `sso_issuer`; local or missing is `ErrNotFound`; a row already on `binding` is `ErrAlreadyBound` with nothing written or revoked, so a concurrent reattach never re-enables a row the IdP disabled under the live issuer. `TestReattachSSOUser` and `TestReattachSkipsARowAlreadyBound` pin it.
- `SetSSORole(userID, role)` writes only the role of an active non-local account (`ErrNotFound` otherwise), so an SSO login never writes back a status it read before a concurrent deactivation, and revokes its grants in the same transaction, row first. `UpdateSCIMUser(scope, u, expectedRole, expectedStatus)` writes only the access the request changes relative to what SCIM read; a removal always lands; a grant lands only if nothing changed the account since, otherwise `ErrAccessChanged` (SCIM 412, retry). The first transaction (only for a removal: expected active to inactive, expected admin to user) locks the row, only if in scope (`lockSSOAccess`), applies only the removal whatever the stored value, revokes (`setSSOAccess`) and commits. The second relocks and rereads the row, applies a grant (expected inactive to active, expected user to admin) only if the stored role and status both still equal the expected ones (as the removal left them), and writes username, email and display name, all or nothing (`ErrNotFound` for a row outside scope or missing, `ErrAlreadyExists` on an exact username clash). Access the request does not change is never written. `betweenSCIMWrites` is the test seam between the two (`SetBetweenSCIMWritesForTest`); `TestUpdateSCIMUserComparesAccessBeforeGranting` uses it. A failure never leaves access the IdP removed and never grants access that was not written. `SetSSORole` writes only the role, so its failure changes nothing; the login handler revokes on a failed demotion. Every purge updates the user row before deleting grants, so app-password issuance, which locks that row, serialises with it; `TestSSOAccessWritesRevokeInTheSameTransaction` pins the writes, `TestSSORoleChangeWaitsForAnIssuanceInFlight` and `TestSCIMAccessChangeWaitsForAnIssuanceInFlight` (internal/api, Postgres) the ordering.
- The directory webhook's writes never set an account active. `RevokeSSOUser(userID, deactivate)` is one transaction on a non-local account: the row first (`status = 'inactive'` when deactivating, else only `updated_at`), then its grants (`grantTables`). `UpdateKySignOnProfile` writes only a `kysignon` account's display name and email. Both are `ErrNotFound` otherwise. `TestWebhookWritesNeverActivate` pins it.
- `BindSignIn(actor, SignInBinding{Disable, Stamp, StampProviders}, settings)` is the sign-in binding as one transaction under `lockedTx("local-admins")`: the actor recheck (`checkActor`; `System` at startup), then every active account of the `Disable` providers deactivated and the grants of every account of those providers deleted (rows first, as in `SetStatus`; idempotent, a second run disables 0), then `Stamp` set as `sso_issuer` on every unstamped non-local account of `StampProviders`, then the settings written (an empty value deletes its key). Any failure writes nothing, so the binding, the disabled accounts and the sign-in keys never disagree. `CountSSOAccounts` is the number it would disable. Local accounts (even with `local` in the list) and calendars are untouched. `TestBindSignInIsOneWrite` pins the rollback on Postgres.
- Migration 5 rebuilds `device_pairings` without the six-digit code column and with `authenticated_at`; pending pairings (90 s) are dropped on upgrade.
- Migration 6 adds `calendars` (owner_kind user|group, per-owner unique slug, `seq`, `min_sync_seq`), `calendar_objects` (unique name and uid per calendar), `calendar_changes` and `calendar_meta` (random `sync_epoch`).
- Migration 7 adds `app_passwords` (id, user_id cascade, label, SHA-256 hex `hash`, `last_used_at`). `AppPasswordStore.Delete` is scoped to the owning user and returns `ErrNotFound` otherwise; `DeleteByUser` revokes all. `Create(by Grantor, p, max)` is one transaction: a `SessionGrantor(sessionHash, passwordHash)` takes the user-row lock through `withPassword` (active, password unchanged), rechecks that session row (the user's, unexpired), then counts against `max` (`ErrQuotaExceeded`) and inserts; a failed lock or recheck is `ErrSessionExpired` and stores nothing, so no credential is minted after a purge that updates the row first (`SetRole`, `SetStatus`, `ReattachSSOUser`, `BindSignIn`, password changes) committed. `Seed` skips the checks (fixtures and tests only; `TestSeedGrantorIsTestOnly` parses every non-test `.go` file in the module and fails on any use); the zero `Grantor` is refused. `TestAppPasswordIssuanceRechecksTheSession` pins it; `TestAppPasswordIssuanceWaitsForThePurge` (Postgres) pins the row-lock wait.
- Migration 8 adds `calendar_grants` (calendar_id and group_id, both `ON DELETE CASCADE`; role `reader|editor|manager`; one row per calendar and group). Deleting a group removes its grants; deleting a calendar removes its objects, changes and grants.
- Migration 9 deletes the sessions of `admin` users whose `sso_provider` is `kysignon` or `scim` (admins the retired global-role webhook could have made); they sign in again and the `roles` claim decides. `TestMigration9RevokesSSOAdminSessions` reruns it over seeded sessions.
- Migration 11 adds `users.sso_issuer` (the sign-in binding, `<kind> <issuer>`, an account was provisioned under) and stamps existing active `kysignon`/`scim` rows with a stored `kyidentity` binding, active `oidc` rows with a stored `oidc` one; inactive rows (possibly a previous issuer's, disabled by an earlier change) and every row of an instance with no binding stay unstamped. `CreateUser` writes it; `UpdateUser` and `UpdateSCIMUser` never do. `TestMigration11StampsTheBoundKind` reruns it.
- Migration 10 adds `groups.source`: `local` by default, every row that existed before it `scim` (SCIM was the only group writer). `Group.Source` is the owner and only the owner writes a group; `ListGroups(..., source)` filters by it (`""` lists every owner); an empty source on insert means `local`.
- Group names are unique ignoring case across both owners. `CreateGroup` and `UpdateGroup` look for a case twin inside `lockedTx("group-names")` and return `ErrAlreadyExists`; `UpdateGroup` checks only when the name changes ignoring case, so a legacy twin stays updatable. `lockedTx` (with `beginTx`/`lockKey`, shared with the calendar quota paths) takes a Postgres transaction-scoped advisory lock at READ COMMITTED (a REPEATABLE READ default would freeze the snapshot before the lock); SQLite's single connection already serialises.
- A group calendar is `owner_kind = 'group'` with `owner_id` = its own calendar ID: no KyIdentity group owns it, so per-owner quotas apply per group calendar. `SetGrant` refuses (`ErrNotFound`) a personal calendar or a missing group; `DeleteGrant` is idempotent; `UserGrants` joins `group_members`, so access follows current membership.
- `CalendarStore.PutObject`/`DeleteObject` run in one transaction: check preconditions (`ErrPreconditionFailed`, `ErrUIDConflict`), bump `calendars.seq`, log one change. Failed writes leave seq and data untouched. `ifMatch` `"*"` means any current version (missing object: `ErrPreconditionFailed` on PUT, `ErrNotFound` on DELETE).
- Owner quotas are enforced atomically in the store: `PutObject` takes `OwnerLimits{MaxObjects, MaxBytes}` (zero = no limit) for the target calendar's owner across all their calendars, and `CreateCalendar` takes `maxPerOwner`. Both take the owner lock (`pg_advisory_xact_lock(hashtextextended('calendar-owner:<kind>:<id>', 0))` on Postgres, which also covers an owner with no rows yet; nothing on SQLite, whose single connection serializes transactions) before the calendar row lock, then count usage excluding the object being replaced (`LENGTH(data)` counts bytes on SQLite BLOB and Postgres BYTEA); over a cap is `ErrQuotaExceeded`. Those transactions begin through `SQLStore.beginTx`, which pins `READ COMMITTED` on Postgres so a server default of `REPEATABLE READ` cannot freeze the snapshot before the lock (SQLite uses the default). `TestConcurrentQuota` pins this on both backends; `TestConcurrentQuotaRepeatableReadDefault` on Postgres.
- `OwnerLimits.MaxTotalBytes` caps every owner's bytes together (excluding the object being replaced). On Postgres it takes the `calendar-total` advisory lock before any owner lock; every writer that takes both uses that order. The total is read from `calendar_usage` (migration 12: one row, backfilled with `SUM(LENGTH(data))`), which triggers on `calendar_objects` (insert, update of `data`, delete, so cascades from calendar and user deletion too) keep in the writing transaction; the check costs one row plus the replaced object's length, never a scan. On Postgres every object write updates that row, so object writes serialise on it at commit; the lock is taken last (after calendar rows), so no cycle forms. `TestCalendarUsageTracksEveryWrite` and `TestMigration12BackfillsUsage` pin it on both backends.
- Migration 14 adds `app_passwords.scope` (`dav` default, so every older row stays a CalDAV device's; `mcp:read`, `mcp:write-own`, `mcp:write-any`) and `mcp_events (token_id, calendar_id, uid)`, cascading with the token and the calendar, so every grant purge (`grantTables`) and calendar delete takes the records too. `Create` refuses any other scope (`ErrInvalidScope`, the empty one included). `SetScope` moves only the user's MCP token between MCP scopes (`ErrNotFound` for a `dav` token or another user's). `ExpireIdle(before, id)` deletes MCP tokens with `COALESCE(last_used_at, created_at) < before` and returns them; each delete repeats the condition, so a token used since the read stays. `TestMigration14ExistingAppPasswordsAreDAV` reruns it over an old row.
- Migration 13 adds `idx_users_username_lower` and `idx_users_email_lower` (expression indexes matching `LOWER(col) = LOWER(?)` lookups), `idx_group_members_user` (`UserGrants` on every DAV request), `idx_mfa_challenges_user` and `idx_pairings_user` (per-user revocation). `TestMigration13LookupsUseIndexes` checks the SQLite plans and the Postgres indexes.
- `DeleteUser` deletes the user's calendars in the same transaction (objects and changes cascade); `calendars.owner_id` has no foreign key, and orphaned bytes would hold the instance cap forever.
- `ListUsers` takes a `UserFilter`: an exact, case-insensitive match on username, email or display name (columns from `userFilterColumns` only). `UserFieldSSOSubject` (SCIM `externalId eq`) is an exact, case-sensitive `sso_subject`. `GroupsByExternalID(externalID, source)` lists one owner's groups with that exact external ID. The admin People list alone uses `UserFieldSearch`, a case-insensitive substring of username, email or display name with `%`, `_` and `\` escaped; SCIM filters stay exact and never map to it.
- `SCIMScope{Issuer, Providers}` is every account SCIM may reach: non-local rows of `Providers` with `sso_issuer = Issuer` (no provider reaches nothing). `Contains` is the Go form, `where()` the SQL one. `UserFilter.SCIM` keeps the rows and the total inside it, `SCIMUserIDs(scope, ids)` returns the IDs in it, `UpdateSCIMUser` locks only a row in it and `DeleteSCIMUser` deletes only one (else `ErrNotFound`), the scope checked in the write's own statement. `TestSCIMScopeListsIDsAndWrites` pins it.
- `CreateSCIMGroup(scope, g)` inserts a `scim` group and its members, `UpdateSCIMGroup(scope, id, change)` locks a `scim` group (`group-names` advisory key, then its row), reads it with its in-scope members, applies `change` (which must not use the store: SQLite has one connection) and writes name, external ID and the in-scope membership difference; each is one transaction and writes nothing on any error: a member out of scope is `ErrInvalidMember`, a taken name `ErrAlreadyExists`, a missing or local group `ErrNotFound`. Memberships outside the scope stay. `TestSCIMGroupWritesAreOneTransaction` pins it.
- Reads return every row or an error: a failed scan or member read is never an empty list (`TestListGroupsReportsAMemberReadFailure`).
- `GetUserByUsername` matches case-insensitively and returns the local account first, then the exact spelling: the unique index is case-sensitive, so a legacy SSO `ADMIN` may exist beside local `admin`.
- `GetObjectByUID` finds an object by its UID within one calendar (UIDs are unique per calendar), for the JSON event API.
- Object ETag is the SHA-256 hex of the stored bytes. `first_start` and `last_end` are unix seconds; NULL `last_end` means unbounded.
- `PruneAudit(before)` deletes audit records created before `before`; `cmd/server` runs it daily with a 365-day horizon.
- `ListObjectsInRange(start, end)` is a superset: `first_start < end AND (last_end IS NULL OR last_end >= start)`, so a zero-length event at `start` is kept (RFC 4791 §9.9); callers apply the exact overlap (`caldav.Match`, `calendar.Expand`).
- `PruneChanges` sets `min_sync_seq` to the highest pruned seq; `ChangesSince` returns `ErrSyncTokenExpired` only when the token seq is below it.
- `Store.ResetAfterRestore` deletes every session, MFA challenge, device pairing and app password (`grantTables`, the same set `revokeGrants` clears per user), writes a new random `sync_epoch` (16 hex) and audits `system.restore_reset` (user `system`, details carry the epoch), in one transaction. Accounts, password hashes, `must_change_password`, recovery codes and calendar data stay as restored: a blanket forced change is no defence against a leaked restored password, so the runbook resets rotated ones by hand. It is idempotent; `cmd/server` runs it after `restore` and from `restore-reset`.
- `store.Open(ctx, cfg)` initializes and auto-migrates the configured database backend.
- SQLite runs with `foreign_keys(ON)` whatever the DSN says (appended last, so it wins; `Open` reads `PRAGMA foreign_keys` and fails startup if it is off: every `ON DELETE CASCADE` depends on it), and `busy_timeout(5000)`, `journal_mode(WAL)` and `synchronous(NORMAL)` unless the DSN sets that pragma itself. `TestSQLiteDSNPragmasKeepForeignKeysOn` pins it.
- PostgreSQL queries are rebound dynamically from standard positional parameters.
- MFA challenges and device pairings are consumed with database state transitions that permit exactly one successful use.
- Recovery-code hash updates use optimistic concurrency so simultaneous redemption cannot reuse a code.
- `CreateSession` stamps `users.last_login_at` with the session's `CreatedAt` in the same transaction; the People list shows it.

- `ApplyInstaller` commits immutable configuration, `signin_bound`, new issuer-bound accounts and native audit together under `local-admins`, then `user-names`; inspection is read-only. Retained drift and existing names or sign-in settings fail instead of being adopted. Native account and sign-in writers refuse owned authority; native sign-in setting writes share the `local-admins` lock with first setup.
- `ApplyInstallerDirectory` fences positive canonical revisions with a retained digest, preserves assigned roles, and atomically changes active status, revokes every `grantTables` row and audits. Deleted directory identities are deactivated, preserving calendars. Owned-session checks verify the exact local ID, issuer/subject, role and binding.
